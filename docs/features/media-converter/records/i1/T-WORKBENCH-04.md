**实现（写集内）**

**`MediaQueue.tsx`**

- **汇总栏**（在队列面板上方）：文件数、源文件总体积、完成数、节省量。节省量只计「压缩视频」，与批次通知的口径相同；没有节省时不显示。
- **标题栏右侧**依次是「清除已完成」「全部取消」「全部开始」（主按钮，位于右上角）。
  - 「全部开始」在以下情况禁用：引擎正在检测或快照未就绪（说明沿用 `engine.detecting_detail`）、引擎不可用（显示原因和建议）、没有待开始的文件。禁用时套一层可聚焦的包装，鼠标悬停和键盘聚焦都能看到原因，原因也通过 `aria-describedby` 读出。
  - 「全部取消」只在有排队或运行中的条目时出现，点击后先弹共享的 `ConfirmDialog`。
  - 「清除已完成」只移除「已完成」的条目，不删除输出文件。
- **开始流程**（`useStartFlow`，行内「开始」与「全部开始」共用）：
  1. 用面板当前的设置，经控制器的计划缓存检查每个待开始的条目：
     - 有损失警告的条目，再按「改为 MKV」的设置问一次计划，损失变少才提供「改为 MKV」；
     - 计划要求 `lossy_to_lossless` 的条目，列为有损转无损。
  2. 根据检查结果开始或弹出确认框：
     - 什么都不用确认，直接 `start`；
     - 有损转无损且选了「覆盖」时，先发一次 `start`。主进程因为这些条目未确认会整次拒绝，借此拿到将被替换的文件，并入同一个确认框；
     - 其他情况先弹确认框。若主进程在确认后才报出将被替换的文件，确认框保持打开并补上这一项，再确认一次。
  3. 确认框每个文件一项，可以「跳过」或「恢复」，有损失的还可以「改为 MKV」：
     - 「改为 MKV」把面板的输出改为 MKV（I1 没有单个文件的设置），然后重新检查。原先有损失、现在没有的条目显示「已改为 MKV，内容会完整保留」；
     - 底部说明「改为 MKV」对本次所有文件生效；
     - 按钮写明「开始 N 个文件」，N 不含跳过的文件。
  4. `start` 拒绝的条目按原因合并为 toast，例如「2 个文件没有开始：当前任务不适用」，即开始时跳过不适用的文件。
  5. 关闭动画期间保留确认框的内容（FK-PIT-0150）；打开时焦点在「取消」上；Esc 只关闭确认框。
- **播报**（`useEndAnnouncements` + `role="log" aria-live="polite" aria-relevant="additions"`）：
  - 页面打开期间，每个条目进入结束状态时追加一行，例如「clip.mp4 已完成，节省 64%」；
  - 页面打开前已结束的条目不再播报；
  - 重试后再次结束（完成时间不同）会再播一次；
  - 播报区保留最近 6 行。
- **失败详情**：`ErrorDetailModal` 依次显示：
  - 错误说明与建议（guide 位置）；
  - 时间；
  - 简短原因，`disk_space_low` 显示需要与可用的空间；
  - 「错误码：xxx」；
  - 脱敏后的日志尾部，逐行列出，可以复制；
  - 关闭动画期间同样保留内容。
- **处理计划的设置**：`usePlanSettings` 同时返回当前设置（供确认框使用）和防抖后的设置（供各行请求计划）。

**`MediaQueueRow.tsx`**

- **按状态显示的操作**（28px 幽灵图标按钮，都带 Tooltip 和 `aria-label`）：

  | 状态 | 操作 |
  | --- | --- |
  | 待开始（可规划） | 开始、移除 |
  | 排队中、运行中 | 取消 |
  | 失败、已取消、已中断、输入已变化 | 重试、移除 |
  | 已完成 | 在文件夹中显示、移除 |
  | 已跳过 | 移除；「仍然转换」在结果行 |

  - 引擎检测中或另一个开始在确认时，行内「开始」禁用；
  - 操作发出后，在条目状态变化前按钮保持忙碌。只有进度变化不会解除忙碌，因为它不替换状态对象。
- **运行中的行**：
  - 状态写「处理中 · 编码中」，右侧依次是百分比、倍速、fps（输出有画面时）、「已写」体积、「剩余」时间。每个数字是右对齐的固定宽度单元，用等宽数字，未知时显示「—」；
  - 时长已知时用 `StudioTaskQueueRow` 的原生进度条；时长未知时是一个不带 value 的原生 `<progress>`，用现有的 `gradient-shift` 关键帧扫光，减少动态效果时不动；
  - 排队中和运行中的行保留「按开始时的设置处理」的计划行。
- **结束的行**：一行状态加结果，最小高度 24px，所以各种结束状态的行同高（68px）。

  | 状态 | 显示 |
  | --- | --- |
  | 已完成 | 「→ 输出名」（中间省略），右侧是「源体积 → 输出体积」和变化。变小为绿色「−64%」，变大为琥珀色「+206%」 |
  | 有多个输出 | 「N 个输出」，下面每个输出一行，带体积和「在文件夹中显示」 |
  | 失败 | 红色「失败」，原因用正文色，右侧「查看详情」 |
  | 部分完成 | 琥珀色「部分完成 m/n」，下面列出已保存的输出 |
  | 已跳过 | 原因，右侧「仍然转换」（按跳过原因 `not_smaller` 或 `already_target` 重试） |
  | 已取消、已中断、输入已变化 | 说明。已有保存的输出时显示「已保存 m/n 个输出」并列出这些输出 |

- **文案映射**：`failureLabels` 覆盖全部 `ItemFailureCode`：
  - 探测类原因复用 `errors.*` 与 `advice.*`；
  - 驱动和设备原因复用引擎徽章的文案；

**渲染审查与修复**

截图都来自 quiet Electron 中的最终代码（最后一次全量运行），共 47 张。设备像素比为 2；1280×800、1080×786、1024×700、786×540 的窗口，页面实际为 1292×806、1092×792、1036×706、798×546（FK-PIT-0188）。审查顺序为方向 → 结构 → 细节 → 交互 → 适配，发现的问题与处理如下：

1. **确认框里的短文件名被截断**
   - 位置：确认框，「pgs.mkv」显示为「pgs.mk」。
   - 原因：`StudioFileName` 把文件名末段限制在自身宽度的 50%，而它的宽度随内容；只有拉伸时末段才有足够空间。
   - 改动：确认框、结果行、输出行中的文件名都加 `[&>.studio-file-name]:flex-1`，做法与队列行、结果卡片相同。
   - 复验：完整显示「pgs.mkv」，超长的输出名在中间省略。
2. **确认框正文与标题、页脚不对齐**
   - 原因：正文内边距 16px，标题和页脚是 12px。
   - 改动：正文改为 12px。
   - 复验：标题、文件卡片、按钮的左右缘对齐。
3. **运行数字的分隔点显得不均**
   - 原因：每个数字有预留宽度，「·」把单元里的空白暴露出来。
   - 改动：去掉分隔点，单元之间留 12px。
   - 复验：三帧中所有单元的位置不变，两行运行条目的数字上下对齐。
4. **已取消的行重复「已取消」**
   - 现象：「已取消 已取消，可以重试」。
   - 改动：说明改为「未完成的临时文件已删除，可以重试」；已中断改为「应用关闭时没有完成，可以重试」。四种语言都改。
5. **结束的行高度不一**
   - 现象：带按钮的行 68px，其余 62px。
   - 改动：结果行最小高度 24px，与 T-WORKBENCH-03 计划行、不适用行的做法相同。
   - 复验：所有结束状态的行都是 68px（列出输出的行除外）。
6. **失败的行两处红色，文字重复**
   - 现象：「失败 编码失败」，状态和原因都是红色。
   - 改动：
     - 原因改用正文色；
     - `encode_failed` 改为「编码过程出错」，`unknown` 改为「原因不明」（en「Encoding error」「Unknown error」，ja、zh-Hant 同步）。
7. **审查数据自相矛盾**（只涉及测试）：注入条目的探测体积沿用了 242 KB 的样本，汇总出现「7.1 MB · 节省 2.7 GB」。改为探测体积等于结果中的源体积，复验后汇总为「44 GB · 节省 2.7 GB」。
8. **786 窄窗口的失败详情截图被 toast 盖住**（只涉及测试）：截图前先等前面切换路由时产生的离开提示消失。

**评审与修复（2026-10-29，独立评审）**

1. **重载后重复播报已经结束的条目**（major，AC-WORKBENCH-04-3「每种结束状态播报一次」）
   - 现象：重载窗口后，以及每次启动后第一次打开本页时，之前已经结束的条目会再被播报一遍。run 场景中，重载后播报区立刻多出一行「pgs.mkv 已完成，节省 64%」。
   - 原因：重载后控制器从空状态开始读取快照，页面先以空列表渲染。`useEndAnnouncements` 把这个空列表当成「页面打开时的状态」，快照一到，列表中所有已结束的条目都被当成刚刚结束。
   - 原测试为什么没发现：重载后的录制器在快照已经应用、行已经显示之后才安装，正好错过这次播报。
   - 改动：钩子增加 `ready` 参数，只在 `state.phase === "ready"` 之后才以当时的列表为基线。测试在重载前用 `page.addInitScript` 安装录制器，从文档创建起就监听；重载后等 pgs 行显示为已完成，再等 500 ms，断言播报区没有新增任何一行。录制器同时能识别「连同文字一起插入的播报区」，每个页面只装一个观察器，再次调用只清空记录。

## 风险与未执行项

**与设计的偏差**（均未改写集外文件）

- **开始前确认没有用共享的 `ConfirmDialog`。** 它只有标题和说明，确认后立即关闭，放不下逐文件的「改为 MKV / 跳过」，也不能在主进程补报将替换的文件时保持打开。所以改用 ScrollableDialog，样式与转写队列的弹窗相同。「全部取消」照设计使用 `ConfirmDialog`。
- **失败原因、建议、跳过原因的映射表放在 `MediaQueueRow.tsx`，不在 `labels.ts`。** `labels.ts` 不在本任务的写集内。新键用 `failure.*`、`failure_advice.*`、`skip.*`，因为设计写的 `errors.<code>` 已被探测失败占用，语义不同。
- **「清除已完成」只移除已完成的条目**（`remove`），没有用 `clear({scope:'finished'})`。后者也会清掉失败、已跳过、已取消的条目，而这些条目还要重试或「仍然转换」。
- **「覆盖」加上有损失、但没有有损转无损的条目时，确认要两轮。** 主进程没有试运行接口，只有在开始时才会列出将被替换的文件，所以在同一个确认框中再确认一次。有有损转无损的条目时只需一轮，因为未确认的条目会让主进程整次拒绝，借此先拿到替换清单。
