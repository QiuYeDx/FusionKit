# 文件名/文件夹名翻译工具：重新设计

日期：2026-10-07。实现基线：`e912824`（v0.3.1 开发分支）。

## 目标与授权

用户要求删除现有 beta 版“文件名/文件夹名翻译工具”，重新设计并实现新版，归属 v0.3.1。要求：

1. 交互符合直觉：能翻译文件名和文件夹名，能按需选择某文件夹下的全部文件与文件夹。
2. 翻译、核对、确认流程清晰，易于使用。
3. 翻译不出错，保存不出错；同时重命名文件夹及其内部条目时不能出错。

先设计并记录在本文，再实现。本轮内部设计决定由实现者完成；进度与验收见文末“任务与验收”。

## 一、旧版问题（源码确认）

### 交互

- 处理范围由全局参数 `scope`（仅自身/直接子项/递归）+ `targetKind` + `maxDepth` 推算。用户生成预览前看不到会处理哪些条目，也不能只勾选文件夹里的某几项。
- 预览只展示前 30 条（`previewLimit`）。剩余条目看不到、不能改，却会被一并应用。
- 任一条目被阻塞（冲突、非法名称等）时，整份计划都不可应用。用户无法简单排除问题项。
- 设置项过多且主次不清：命名风格、双语分隔符、技术标记保留、冲突策略、深度等。还叠加了引导 Tour、风险确认弹窗和 toast，状态分散在多个面板里。

### 后端与数据

- 规划在渲染进程完成，计划存放在内存 Map 中（30 分钟过期，最多 10 份），页面刷新即丢失。完整计划连同路径从渲染进程整包发给主进程执行。
- 应用中途失败时不会自动回滚。已经改成临时名 `.fusionkit-renaming-*.tmp` 的条目会以隐藏的临时名留在磁盘上，需要用户自己点回滚。进程崩溃后也没有恢复入口。
- 文件夹与其子项同时改名依赖两阶段临时名，外加多轮前缀改写（`rewritePathPrefix`），逻辑复杂且难以验证。日志每走一步就整文件重写一次，成本为 O(n²)。
- `fs.rename` 遇到已存在的目标文件会直接覆盖。旧实现只在执行前统一检查一次，没有在每一步紧贴执行做不覆盖检查。
- 翻译在渲染进程中用 ai-sdk 直连模型，与其他工具使用的主进程模型运行时（代理、重试、错误分类）不一致。

结论：保留可复用的经验（受保护路径、Windows 保留名、模型 JSON 修复），删除旧页面、旧服务和旧主进程模块，按本文重建。

## 二、使用流程

一页完成，四步，每一步都有清楚的可见状态：

```text
① 添加文件/文件夹  →  ② 在列表中勾选要改名的条目  →  ③ 翻译并核对、修改新名称  →  ④ 确认重命名（可撤销）
```

### 2.1 页面结构

```text
┌ 添加条目 ───────────────┐  ┌ 条目  23 ────────────────── [选择 ▾] [全部|已选|问题 2] [清空] ┐
│ 拖入文件或文件夹         │  │ ☐  名称                       新名称                     状态 │
│ [添加文件] [添加文件夹]   │  │ ▾ ☑ 📁 アニメ資料              动画资料                     ✓   │
└─────────────────────────┘  │   ▸ ☐ 📁 第1期    内含 0/12  [选择内部全部]                 │
┌ 翻译设置 ───────────────┐  │     ☑ 📄 第1話.mp4             第1集.mp4                    ✓   │
│ 目标语言  [简体中文 ▾]   │  │     ☑ 📄 第2話.mp4             第2集.mp4                    ⚠   │
│ 源语言    [自动检测 ▾]   │  │     ☐ 📄 cover.jpg             —                                │
│ 名称格式  [仅译名|…]     │  ├──────────────────────────────────────────────────────────────┤
│ 包含隐藏项  ○            │  │ 已选 3 项 · 已翻译 3 · 1 个问题      [重新翻译]  [重命名 2 项] │
│ ▸ 补充要求               │  └──────────────────────────────────────────────────────────────┘
└─────────────────────────┘
```

- 左侧配置列（320px）：“添加条目”与“翻译设置”。窄窗口时条目列表排在前面（FK-PIT-0083）。
- 右侧主区：异常恢复提示和最近结果（按需出现），下面是唯一的工作面板“条目”。翻译、核对和应用都在这个面板里完成，不再拆成多个预览/应用面板。
- 未配置任务执行模型时，主区顶部显示提示和“前往设置”。列表仍可以添加和勾选，只禁用翻译。

### 2.2 添加条目

- 拖入或点按钮选择，可以混合添加文件和文件夹。Windows 的系统对话框无法同时选文件和文件夹，所以提供两个按钮。
- 添加的条目成为列表的“根条目”。同一路径重复添加会被忽略。
  - 新条目位于已有根条目之内时，不另建根条目，而是展开到它并勾选。
  - 新条目包含已有根条目时，它成为新的根，原来的根变成它的后代。勾选和译名按路径保存，不会丢失。
- 默认行为：
  - 添加的条目本身会被勾选，与“我拖进来的就是要处理的”这一直觉一致。
  - 文件夹根条目自动展开一层，直接看到其中内容。
  - 文件夹行显示“内含 x/y 已选”，以及“选择内部全部”快捷操作。
- 以下路径拒绝添加，并在添加区下方用一行说明原因：不存在、受保护路径（磁盘根、用户主目录、系统目录）、Windows 资源管理器生成的临时代理路径（FK-PIT-0099）。临时代理路径会提示改用“添加文件”按钮。

### 2.3 选择语义（核心）

**每一行的复选框只表示“重命名这一项”，不级联。** 文件夹自身的名称和其中内容是两件独立的事。传统级联复选框会把“改文件夹名”和“改内部所有条目名”混在一起，正是用户此前难以表达意图的根源。

级联需求通过显式、命名清楚的批量操作完成：

| 入口 | 操作 |
| --- | --- |
| 文件夹行“选择内部全部”（悬停/聚焦时出现；内部未全选时常显于行内提示旁） | 递归加载该文件夹全部后代并勾选（不含文件夹自身） |
| 文件夹行 ⋯ 菜单 | 选择内部全部 / 仅选择内部文件 / 仅选择内部文件夹 / 仅选择直接子项 / 取消选择内部 |
| 面板“选择”菜单 | 全选（含所有子文件夹内容）/ 仅文件 / 仅文件夹 / 仅根条目 / 取消全选 |

- 递归选择由主进程收集后代：跳过符号链接目录，按设置排除隐藏项，单次上限 20,000 项。超过上限会提示并截断，不会静默漏选。
- 文件夹行显示后代勾选数（“内含 3/40 已选”），让用户在不展开的情况下也知道内部状态。
- 视图筛选：全部 / 已选（只显示已勾选的条目及其祖先路径）/ 问题（只显示有问题的条目）。

### 2.4 翻译与核对

- 主按钮随状态变化，每一刻只有一个明确的下一步：
  - 有已勾选但尚未翻译的条目时，主按钮为“翻译 N 项”，“重命名”不可用（Tooltip 说明原因）。
  - 全部已翻译后，主按钮变为“重命名 N 项”，次按钮为“重新翻译”。
  - 翻译中，底栏显示进度条、“已完成 x/N”和“停止”。
- 新名称列：
  - 显示最终名称：扩展名、名称格式都已应用。名称不变时显示“无需更改”，并以弱化样式呈现。
  - 单击或按 Enter 进入行内编辑，编辑的是完整名称。Enter / 失焦提交，Esc 取消。手动修改过的条目带“已编辑”标记。
  - 行菜单提供：重新翻译此项、恢复为翻译结果、保留原名（取消勾选）。
- 状态列：待翻译 · 翻译中 · 就绪 · 无需更改 · 翻译失败（可重试）· 问题（Tooltip 给出原因和修复建议）。
- “重新翻译”只覆盖未手动编辑的条目；单项“重新翻译此项”会覆盖该项的编辑。
- 修改设置（目标语言、名称格式等）后：
  - 名称格式只影响名称组合，不重新请求模型，新名称立即刷新。
  - 语言或补充要求变化后，已翻译条目标为“待重新翻译”，主按钮提示重新翻译。

### 2.5 问题检测（随编辑实时更新）

渲染进程实时检测，主进程在确认前与执行前权威复检：

| 问题 | 说明 |
| --- | --- |
| 名称为空 / `.` / `..` | 不可用 |
| 非法字符 `\ / : * ? " < > \|` 与控制字符 | 自动替换只针对模型输出；手动输入时提示 |
| Windows 保留名（CON、PRN、AUX、NUL、COM1–9、LPT1–9，含带扩展名形式） | 所有平台统一禁止，保证跨平台可用 |
| 末尾是点或空格 | 不可用 |
| 超过 255 个字符或 255 字节（UTF-8） | 不静默截断，要求用户修改 |
| 同一文件夹内新名称重复 | Windows/macOS 不区分大小写，并做 Unicode NFC 归一化 |
| 与同一文件夹内未改名的现有条目重名 | 被同批改走的名称视为已释放；根条目所在目录由主进程检查 |

- 有问题的条目不会阻塞其他条目，只是不参与本次重命名。
- 底栏和确认弹窗明确显示“将跳过 N 个有问题的条目”。
- 对于同一文件夹内的重复名称，提供“自动编号”快捷修复：按原名称顺序追加 ` (2)`、` (3)`。

### 2.6 确认与执行

点击“重命名 N 项”：

1. 主进程预检（与执行时的校验完全相同，只是不改动磁盘），把结果标注到对应行。
2. 打开确认弹窗（ScrollableDialog）：
   - 摘要：文件 N · 文件夹 M · 跳过 K。
   - 变更清单：按所在文件夹分组，每行显示“原名 → 新名”，长名称用中间省略并提供完整 Tooltip。
   - 跳过清单：默认折叠，列出原因。
   - 一行说明：完成后可在本页撤销。
3. 点“开始重命名”。执行期间弹窗不可关闭并显示进度；预检后到执行时如有变化，主进程会再次拒绝并说明原因。
4. 结果：
   - 全部成功：关闭弹窗，主区顶部显示“已重命名 N 项”和“撤销”。列表按新路径刷新，保留展开状态，清空本批勾选与译名。
   - 失败：主进程已自动把已完成的步骤全部撤销，磁盘恢复原状。弹窗显示失败条目与系统原因，列表保持原样，方便修改后重试。
   - 撤销本身也失败时（例如文件被占用）：列出无法恢复的具体路径，并保留“重试恢复”入口，绝不静默。

## 三、名称组成规则

- **扩展名**：只有文件有扩展名。扩展名取最后一个点之后 1–10 位字母或数字（如 `.mp4`、`.json`）。另识别 `.tar.gz`、`.tar.bz2`、`.tar.xz` 等复合扩展名。
  - 不符合规则的点段属于名称本身，例如 `Mr. Smith notes` 没有扩展名。
  - 以点开头的名称（`.env`）整体视为名称主体，并保留前导点。
  - 文件夹名称中的点不当作扩展名。
- **只把名称主体交给模型**，扩展名在本地原样附回，因此模型无法改动或丢失扩展名。
- **名称格式**：
  - 仅译名：`第1集.mp4`
  - 译名 (原名)：`第1集 (第1話).mp4`
  - 原名 (译名)：`第1話 (第1集).mp4`
  - 若译名与原名相同，两种双语格式都只保留一份，不产生 `X (X)`。
- **模型输出清理**：
  - 去除换行与控制字符，合并连续空白，去掉首尾空白以及末尾的点和空格。
  - 非法字符按目标语言替换：
    - 中文、日文、韩文：替换为全角形式（`：` `？` `／` 等）。
    - 其他语言：`:` 改为 ` -`，`/ \ |` 改为 `-`，`< >` 改为 `( )`，`"` 改为 `'`，`* ?` 删除。
- **无需翻译的快捷路径**：名称主体不含任何字母（纯数字、日期、符号）时，本地直接判定为“无需更改”，不请求模型。

## 四、架构

```text
渲染进程                                     主进程 electron/main/name-translation/
pages/Tools/Rename/NameTranslator  ──┐
store/tools/rename (会话 + 配置)      │  window.nameTranslation（专用 preload API，精确白名单）
services/name-translation  ──────────┼──► ipc.ts ─┬─ fs-listing.ts   列目录 / 收集后代 / 检查添加路径
  naming.ts   名称组成与校验（纯函数）  │           ├─ translator.ts   提示词 + 模型运行时 + JSON 解析
  translate.ts 批次、并发、取消        │           ├─ planner.ts      权威校验（预检与执行共用）
  agentPlan.ts HomeAgent 计划          │           ├─ executor.ts     执行 / 自动回滚 / 撤销
HomeAgent 工具与卡片 ─────────────────┘           └─ journal.ts      JSONL 操作日志
共享协议：src/type/nameTranslationIpc.ts（渲染与主进程共用类型、通道和请求校验）
```

- 文件系统与改名由主进程负责。渲染进程只提交 `{路径, 类型, 身份, 新名称}`。主进程不信任渲染进程算出的任何目标路径，所有目标路径都由主进程自己计算。
- 翻译请求在主进程执行，复用 `sendModelRuntimeText`，与文本翻译一样获得代理、重试与错误分类。批次、并发和取消由渲染进程编排，便于展示逐项进度。
- 新增 `window.nameTranslation` 预加载 API，只暴露固定方法。旧的通用 `ipcRenderer` 桥拒绝 `name-translation:` 前缀（FK-PIT-0007）。生产主进程组合中必须注册对应处理器，并有测试覆盖（FK-PIT-0079）。

### 4.1 IPC 方法

| 方法 | 作用 |
| --- | --- |
| `selectPaths({ kind: "file" \| "directory" })` | 系统对话框，多选 |
| `inspectPaths({ paths, source })` | 返回可添加的条目信息与拒绝原因 |
| `listDirectory({ path, includeHidden })` | 懒加载一层（单目录上限 5,000，超出时标注截断） |
| `collectDescendants({ path, includeHidden })` | 递归收集，返回按目录分组的条目（上限 20,000） |
| `translate({ requestId, model, sourceLang, targetLang, instructions, items })` | 一个批次的翻译 |
| `cancelTranslate({ requestId })` | 取消该请求下所有进行中的模型调用 |
| `preflight({ items })` / `apply({ items })` | 权威校验 / 执行（同一套校验） |
| `undo({ journalId })` | 撤销一次已完成的重命名，可重复调用续做 |
| `listJournals()` | 最近记录与未完成记录（用于恢复提示） |

条目身份由 `lstat(bigint)` 的 `dev + ino` 组成，以字符串传递。Windows 上 Node 的 `ino` 即 NTFS FileId（FK-PIT-0063）。执行前比对身份，确认路径没有被替换成另一个文件或文件夹；若平台不提供 ino（为 0），则退化为只比对类型。

## 五、执行算法（保存不出错的关键）

输入为若干 `{ path, kind, identity, newName }`。

1. **规范化与校验**：
   - `path.resolve` 后去重。
   - 名称合法性检查（同 2.5）。
   - `lstat` 确认条目存在、类型一致、身份一致。
   - 拒绝受保护路径及其内部条目（磁盘根、用户主目录本身、系统目录）。
   - 新名称与原名逐字节相同的条目直接跳过。
2. **按父目录分组**，每组读取一次真实目录内容：
   - 组内新名称两两不能重复（Windows/macOS 不区分大小写，并做 NFC 归一化）。
   - 新名称不能与组内未参与改名的现有条目重名。被同组其他条目改走的名称视为已释放。
3. **由深到浅执行**：按父目录深度降序处理各组。
   - 改名只会影响该条目自身及其后代的路径，而后代所在的更深的组已经先完成。同层各组互不包含。
   - 因此每一步使用的都是磁盘上仍然有效的原始路径，不需要任何前缀改写。这正是“同时翻译文件夹及其子项不出错”的保证。
4. **组内顺序**：
   - 若组内某个新名称占用了组内另一条目的原名（链式 `A→B, B→C`、互换 `A↔B`，或 Windows/macOS 上只改大小写），该组整体分两步执行：先全部改为唯一临时名 `.fk-rename-<随机>-<序号>`，再改为最终名。
   - 否则每项直接一步改名。临时名只在必要时出现，存在时间最短。
5. **每一步改名前都紧贴检查目标不存在**（`lstat`）。如果目标已存在，立即中止，防止 `fs.rename` 覆盖文件。
6. **每一步完成后先追加日志**（JSONL，`appendFile`，O(n)），再继续下一步。
   - Windows 上遇到 `EBUSY`/`EPERM`/`EACCES` 这类暂时性锁时，有限重试 3 次（FK-PIT-0105）。
7. **任何一步失败**：按相反顺序逐一反向执行已完成的步骤（`to → from`，同样先检查 `from` 不存在），把磁盘恢复原状。
   - 结果中区分三种情况：已回滚、部分无法回滚（逐条列出路径）、日志写入失败。
8. **成功**：
   - 日志标记为 completed。
   - 返回每项的原路径到最终路径的映射。最终路径由主进程按“祖先改名由浅到深依次替换”计算。

**撤销**：从日志按相反顺序反向执行每一步，执行前确认 `to` 存在且 `from` 不存在。每撤销一步就追加 `undone` 记录，因此中途失败后可以再次撤销，接着完成剩下的步骤。

**崩溃恢复**：进程在执行途中退出时，日志停留在 running 状态。下次打开工具时，页面顶部提示“上次重命名未完成”，提供：
- “恢复原名”：对已完成的步骤执行撤销。
- “保留现状”：把该记录标记为已处理。

**日志**：`userData/name-translation/journals/<id>.jsonl`。
- 第一行是头部（版本、时间、条目数），之后是 `step`、`status`、`undone` 记录。
- 解析时容忍最后一行被截断。
- 保留最近 30 份。
- 日志中只记录路径，不记录模型内容和 API Key。

## 六、翻译

- **批次**：
  - 按父目录分组，同一文件夹下的兄弟条目放进同一批，让模型看到上下文、保持一致，例如剧集编号的写法。
  - 每批最多 40 项或约 3,000 字符。
  - 渲染进程最多同时发 3 批。
- **请求内容**：
  - 批内编号 `1..n`（短 id，减少模型错配）。
  - 每项给出名称主体和类型（文件/文件夹）。
  - 附带所在文件夹的最后两级路径作为上下文。
  - 附带用户的补充要求。
- **提示词规则**：
  - 只翻译自然语言部分。
  - 保留数字、日期、季集编号格式（`S01E02`）、版本号、分辨率与编码标记、方括号中的发布组标签。
  - 已经是目标语言时原样返回。
  - 不输出扩展名、路径分隔符或非法字符。
  - 严格返回 `{"items":[{"id":"1","name":"…"}]}`。
- **解析**：
  - 去除 `<think>` 和 Markdown 代码围栏，提取第一个平衡的 JSON 对象。
  - 逐项校验 id。缺失或重复的 id 视为该项失败，多余的 id 忽略。
  - 一批中失败的条目会单独再试一次（拆成更小的批），仍失败则标为“翻译失败”，可单独重试，不影响其他条目。
- **错误**：
  - 鉴权、额度、模型不存在这类错误不可恢复，直接停止整次翻译并显示原因。
  - 限流与网络抖动由模型运行时重试。
  - 用户点“停止”后，已完成的批次保留结果，未完成的条目回到待翻译。
