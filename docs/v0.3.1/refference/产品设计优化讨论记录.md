看完这个分支后，我的判断是：**需要做的不是再补一点说明、折叠几个选项，或者把卡片画得更漂亮，而是重新组织用户的操作流程。**

目前的实现更像一个“翻译知识的管理后台”：用户得先理解资料怎么分类、如何获得采纳、适用范围怎样表达、风格与方案如何组合，才能把资料用于翻译。但用户真正想做的通常只是：

> **“以后这个词这样翻译。”
> “翻译这个主播的视频时，参考这些背景。”
> “这次用这两份资料，先试几句。”**

这两者之间的距离，正是现在“拒之门外”的主要原因。

本次审查基于分支当前提交 **`662ca2d`**，重点查看了资料管理、条目编辑、方案编辑、工作台资料选择以及实际执行筛选逻辑。以下属于源码和交互路径审查，没有运行 Electron 做真机操作测试。

## 一、目前到底哪里不顺：不只是概念多，还有一些行为违背直觉

### 1. 用户必须同时理解两套“这份资料属于谁”

当前界面同时存在“内容对象”和“资料集”；条目里又有“用于分类的关联对象”和“适用范围中的对象角色”。文案明确说明：关联对象只用于分类，不决定何时使用；真正限制使用的是另一组对象与角色条件，而且多个条件需要同时满足。

这在数据模型上可以成立，但普通用户很容易产生一个合理预期：

> 我把资料放进了“某游戏”的资料集，也关联了这个游戏。翻译时选了这份资料，应该就能使用。

**现在这个预期不一定成立，而且创建默认值进一步加重了困惑。**

`newEntry()` 会把当前选中的对象，或者资料集关联的对象，自动复制成条目的使用条件：人物默认是 `present`，其他对象默认是 `topic`。执行时，如果没有对应的任务绑定，又会以 `subject_unbound` 排除资料。

因此，按源码可以推导出这样一条容易踩中的路径：

```text
建立一个关联某游戏的资料集
        ↓
添加术语时，自动带上“该游戏必须是主题”的条件
        ↓
翻译时选择这个资料集
        ↓
但没有再选择“全文主题”
        ↓
术语没有被使用
```

问题不是范围校验不该存在，而是：**“我正在什么分类下面浏览”，不应该悄悄变成“执行时必须满足什么条件”。**

这是我认为最需要优先修正的地方之一。

### 2. 手工维护也被当成了审核流程

`EntryEditor` 中的 `adopt` 默认是 `false`，保存时据此将条目设为 `ready` 或 `candidate`。这个默认值也用于编辑已有条目。也就是说，从表单提交逻辑看，**编辑一条已采纳资料后，如果没有重新勾选采纳，提交的状态会变成候选**。

对于外部导入、AI 提议，这种谨慎合理；但对于用户自己主动维护的内容，交互就显得别扭：

> 我亲手把错字改对了，为什么保存后反而不能用了？

应该保留“新版本需要新的采纳记录”这一安全机制，但把用户动作改为清楚的 **“保存并应用”**，一次操作完成保存与对当前版本的明确确认，而不是让用户每次找一个额外的勾选框。

### 3. “规则—风格—方案”的组合能力，变成了前置学习成本

当前风格至少要引用一条已经建立的规则；方案再选择资料集、基础风格、补充风格、翻译要求、内容说明以及对象角色建议。

这里要区分两件事：**当前并不是必须创建方案才能翻译，直接选资料集已经可以。**但是，界面把这些管理入口并列摆出来，会让用户不确定：

* 我只想“翻译得口语化一些”，应该写翻译要求，还是建规则，还是建风格？
* 给一个主播设置说话特点，是背景、表达习惯，还是风格？
* 资料维护好了，是否还得包一层方案才能使用？

问题不是功能重复到完全没有区别，而是**这些区别不应该成为开始使用之前的考试题**。

### 4. 可维护的内容，比实际能用于翻译的内容更多

资料编辑器提供术语、背景、规则、表达习惯和参考译文；但执行器明确跳过 `expression` 和 `memory`。界面也说明，全局偏好继承和自动积累尚未启用。

现在虽然加了“仅保存”“暂不参与执行”的提示，但用户仍然会面对这些入口，并花精力理解、填写它们。

**没有兑现使用价值的功能，不应该与已经生效的功能平等地出现在日常主流程里。**保留兼容和查看能力没有问题，但不宜继续鼓励用户从这些类型开始建设资料库。

### 5. 工作台不是没接通，而是像打开了“另一套翻译工具”

当前路径大致是：

```text
打开翻译弹窗
→ 开启“使用翻译资料”
→ 打开另一层资料翻译弹窗
→ 设置原文语言、资料集或方案、全文主题等
→ 检查
→ 开始翻译
```

开启资料后，外层原本的翻译操作被切换为资料入口，真正的检查和启动放在子弹窗。单文件、批量又分别有对应的资料组件；切换文档时，普通翻译入口中的资料开关还会被重置为关闭。

此外，全文翻译中的逐句人物或条件调整，还需要借助片段试译中的范围设置。这是技术实现路径影响产品操作路径的明显例子。

**“使用资料”应该是翻译的一项配置，而不应该让用户感觉自己切换到了另一个更复杂的产品。**

### 6. 还有一个会放大“怎么用了也不对”的执行问题

当前规则冲突判断中，**同一 `dimension` 的两条规则，只要文本摘要不同，就被视为冲突**。两条都是非强制规则时，会从对应字幕的适用项中同时排除；两条都是强制规则时，会产生错误。

例如，下面是一个按该逻辑构造的示例：

```text
规则 A：使用自然口语。
规则 B：避免生硬的书面表达。
```

它们可能完全互补，但如果放在同一个规则维度，就可能被当作冲突。

这不是靠 UI 解释能解决的问题。**同维度不等于语义矛盾**，这段策略应与交互一起修改，否则用户越认真维护，越容易得到反直觉结果。

## 二、我建议的核心改法：前台以“资料集”为唯一的日常组织入口

我不建议推翻现有底层结构，也不建议再创造一个“知识空间”“资料包”“主体档案”等新名词。

**沿用现有“资料集”，但让它真正成为用户维护和选用资料的主角。**

用户只需要知道：

> 一份资料集，就是翻译某类内容时可以选用的一份资料。
> 里面可以有固定译法、背景说明和翻译要求。

比如，以下都是合理的资料集名称：

```text
主播 A
游戏 B
某系列视频
我的字幕通用规范
```

用户可以组合选用“主播 A + 游戏 B”，不必先建立一套完整的对象目录。

### 现有概念如何安置

| 现有能力         | 建议在产品中的位置                                |
| ------------ | ---------------------------------------- |
| 资料集          | 日常维护、查找和翻译选用的主入口。                        |
| 内容对象         | 作为关联信息保留；有需要时再设置，不再与资料集并列成为必学导航。         |
| 术语、背景、规则     | 呈现为“固定译法、背景说明、翻译要求”，直接在资料集内维护。           |
| 风格           | 让用户直接写或选择口吻要求，不必先创建底层规则再引用。              |
| 方案           | 在实际选好资料和要求后，通过“保存本次设置”形成，而不是从空白配置开始。     |
| 来源、修订、复杂适用条件 | 保留在详情或高级设置中，由系统自动维护能自动维护的部分。             |
| 表达习惯、参考译文    | 现阶段不放进主要新增入口；已有内容仍可查看、整理和导出，并标明“暂不用于翻译”。 |

这里不是把 `Subject` 和 `Collection` 在数据库里合并，而是**不再要求用户日常操作时同时管理两套组织结构**。

也不是把所有东西塞进一个 Markdown 大文本框：术语依然适合结构化维护，背景适合文本编辑，翻译要求适合简短规则；它们只是共享同一个清楚的使用入口。

## 三、资料模块应该怎么改：让维护资料像写内容，而不是填数据库表单

### 1. 首页改为“资料集列表 + 当前资料”，不要以筛选控制台开场

现在已经有使用指南，也已经把部分高级字段折叠起来了；但页面仍然围绕对象筛选、资料集筛选、类型、语言、状态和管理视图展开。因此再增加一段教程，改善会比较有限。

我建议的结构如下，内容和数量仅为示意：

```text
翻译资料                                 搜索资料    ＋ 新建资料集

我的资料集              游戏 B
                        用于游戏 B 的字幕翻译                ⋯
全部资料
主播 A                  固定译法    背景说明    翻译要求
游戏 B  ←
通用字幕规范            搜索原词或译法                  ＋ 添加译法
────────────────
待确认 · 3              原词             译法              备注
归档                    checkpoint       存档点
                        ...
                        ＋ 直接输入一条

                        支持粘贴多行术语
```

几个关键变化：

**左侧是可以直接识别的资料集名称，而不是两个需要展开才能看见内容的下拉框。**对象、语言和状态在必要时作为过滤条件，不占据默认操作中心。

**主区首先显示用户写的内容。**来源、版本、复杂条件进入详情面板，不让每一行都变成一组状态徽章和元数据。

**“待确认”保留为工作队列，而不是所有用户都必须经过的第二站。**没有待确认内容时，它不应该抢占注意力。

### 2. 新建资料集只问真正必要的信息

普通路径只需要：

```text
名称：游戏 B
翻译方向：日语 → 简体中文
```

翻译方向可以继承当前任务或最近一次选择，用户可以修改。对象、标签、复杂说明都不是创建前提。

资料集创建后，直接进入可编辑状态，而不是继续要求用户完成“对象—分类—规则—风格—方案”的配置。

### 3. 术语应该支持直接编辑和批量粘贴

高频维护路径应该是：

```text
输入原词 → 输入译法 → Enter 保存并继续下一条
```

默认只露出“原词”和“译法”，必要时加一个简短备注。别名、大小写、匹配模式、强制程度等，放进单条详情。

批量录入则应该允许粘贴类似：

```text
checkpoint    存档点
save slot     存档槽
```

系统先解析成可编辑预览，用户检查后一次确认。CSV、TSV、从表格复制的内容，也都应该走这个日常导入入口。

当前拖放入口只接受单个 `.fktk.json` 文件，这适合完整资料交换，但不够贴近日常“我手上有一张术语表/一段整理好的文本”的输入方式。

**知识包导入和日常内容录入，应当是两条不同的产品路径。**

### 4. 背景说明和翻译要求，直接写就行

“背景说明”应该允许直接粘贴一段介绍，来源为可选项；“翻译要求”则可以直接写：

> 使用自然口语；保留人物称呼；不要擅自补充原文没有的信息。

用户不需要先回答“这是 register 还是 fidelity”，更不需要先建立规则条目，再创建一个引用它的风格。

底层需要结构化引用时，由应用在保存时生成关联记录。**前台不必一比一复刻这些关系。**

不过，“背景信息尚不确定”“仅限某个语境”这类会影响正确性的属性，仍应有清楚的设置入口，不能为了减少字段而把不确定内容包装成事实。

### 5. 根据来源决定确认方式，而不是对所有内容统一审核

建议这样区分：

| 内容来源            | 默认操作                     |
| --------------- | ------------------------ |
| 用户亲手新增或修改       | **保存并应用**；可另选“保存草稿”。     |
| 粘贴后由确定性规则拆分的术语表 | 展示解析预览，用户确认后添加并应用。       |
| 外部知识包           | 保留内容、范围、冲突预览，由用户明确确认。    |
| AI 提取或推断的资料     | 进入“待确认”，不自行成为可信内容。       |
| 正在执行的翻译任务       | 继续使用提交时固定的版本，不被后续编辑悄悄改变。 |

“保存并应用”也需要明确一句：

> 将用于之后使用这份资料的新翻译；不会修改已经生成的译文。

这样既简化日常操作，也没有丢掉现有的来源与版本边界。

## 四、工作台怎么改：只有一个翻译流程，资料就在其中

这是另一半关键改造。资料模块再好用，工作台还是现在的多层配置路径，整体体验依然不会顺。

### 1. 模型、语言、资料、要求，放在同一个翻译面板里

建议结构如下，匹配数量仍为示意：

```text
翻译字幕

原文语言  日语                  目标语言  简体中文
翻译模型  当前模型

本次使用的资料
[ 主播 A  × ]  [ 游戏 B  × ]               ＋ 选择资料

本次翻译要求
[ 使用自然口语，保留原文语气……                  ]

资料检查
将纳入 12 条术语、2 段背景                     查看
有 1 项译法冲突需要处理                       处理

更多设置

保存本次设置                     试译几句      开始翻译
```

**不要先让用户开启一个开关，再去另一个弹窗开始另一套配置。**

默认未选资料就显示“未使用资料”；选了就显示名称。选择资料可以用轻量选择器，新增或编辑可以用侧边面板，但始终保留当前文件、模型、语言和翻译要求的上下文。

片段试译继续保留，但成为“用当前设置先试几句”，而不是独立模式中才有某些必要配置。

### 2. 不要让用户为了使用资料，再重复声明一次资料的分类

建议区分普通资料和真正需要身份约束的资料。

**普通固定译法、一般背景：**用户主动选用资料集之后，在语言正确、条目已确认、内容匹配的情况下即可参与。不要因为用户添加时所在的浏览分类，额外生成一个隐含主题门槛。

**确实有限定条件的资料：**选择时就显示人话提示，例如：

> 这份资料中的 4 条译法仅适用于“游戏 B”。本次字幕是否属于该游戏？

需要确认的范围集中解决一次，而不是让用户到另一个区域自己猜要勾选什么。

**人物口吻、说话者专属表达：**仍然不能因为选了“主播 A”的资料集，就假定每句话都是 A 说的。应当提供明确的范围设置，例如“整份字幕均为 A 发言”或“仅用于选中的片段”；多人对话再进入更细的设置。

简化的是**填写方式**，不是取消身份与语境的正确性要求。

### 3. 检查应融入“开始翻译”，而不是让用户学习计划生成流程

当前本地检查与模型请求已经有明确区分，可以利用这套能力改善交互。

建议在资料或配置变化后，自动刷新本地检查结果；也可以在用户点击“开始翻译”时先完成检查。

无阻塞问题就继续；有真正冲突就停在原面板，给出解决动作。**自动进行本地检查，不代表自动发送付费模型请求**，模型请求仍应由用户明确点击“开始翻译”或“试译”触发。

底层的计划、摘要、过期和版本一致性检查可以保留，不需要变成用户必须手动推进的每一个步骤。

### 4. 不仅告诉用户“选了”，还要告诉用户“会用哪些、为什么没用”

目前已经存在检查结果、纳入条目数量和执行记录，并不是完全没有反馈；但可以把它们变成更贴近日常理解的呈现。

例如，在“查看本次资料”中显示：

```text
将使用
checkpoint → 存档点
在第 12、38 条字幕中出现
来源：游戏 B

本次未使用
save slot → 存档槽
原因：原文没有出现该词

需要处理
某术语存在两种不同译法
[ 使用译法 A ] [ 使用译法 B ] [ 本次不使用 ]
```

这里有三个不同层次，不能混为一谈：

**已选择资料集 → 实际纳入模型请求 → 模型是否遵循。**

前两项可以通过系统记录准确展示；第三项只能通过译文检查提供证据或疑点，不能因为“发送了资料”就显示“已正确应用”。

同时，“某术语没有在原文出现”是正常情况，应该收进未使用详情，不该和真正的冲突混成一长串警告。

### 5. 记住选择，但不要记住错误的语境授权

同一文档再次翻译，应保留上次选用的资料和要求；新文档可以提供“沿用上次设置”，或者选一个已保存设置。

但复用时需要区分：

> 资料集选择、一般翻译要求，可以复用。
> 逐句说话人绑定、特殊条件确认，不能不经检查就套到新字幕上。

这样既避免每次重配，也不会为了方便而误用人物资料。

## 五、维护资料最好的入口，有一部分应该在工作台，而不是资料管理页

用户最容易发现资料缺失或译法错误的地方，是看译文的时候。

因此，我会把下面这条路径列为高优先级：

```text
发现一个词翻译不对
        ↓
改正译文，或选中原词与正确译法
        ↓
“记住这个译法”
        ↓
预填原词、译法、翻译方向和资料集
        ↓
确认保存，之后可复用
```

不要让用户看完字幕后，再去资料管理页重新输入一遍，还要重新选择语言、对象、角色和状态。

同时注意：**修改一句译文，不等于已经得到一条可以全局套用的术语。**例如整句措辞修正不能机械地提取成固定词义，保存前应让用户确认原词边界、适用范围和目标资料集。

当前执行器还不使用参考译文，所以第一阶段可以先把“记住固定译法”做实；等参考译文真正接入翻译，再提供“保存为参考译文”。不要先堆出一个看起来完整、实际上不会参与翻译的学习闭环。

AI 辅助整理也适合放在这里或资料集内部：

> 粘贴一段内容 → AI 整理出建议术语和背景 → 用户确认 → 加入资料集。

AI 应该减少录入负担，而不是让用户为了使用 AI，又多管理一层知识结构。

---

## 六、怎么落地：保留底层能力，优先改最短使用路径

我建议分三个阶段，而不是直接重写整个知识系统。

### 第一阶段：先让“一条术语确实用起来”

| 改造重点                         | 主要涉及位置                                             |
| ---------------------------- | -------------------------------------------------- |
| 手工新增、修改改为明确的“保存并应用”，草稿作为次要操作 | `EntryEditor.tsx`                                  |
| 不再把浏览分类隐式转成新条目的执行条件          | `model.ts`、条目范围设置                                  |
| 日常首页围绕资料集与内容，弱化对象、方案、治理入口    | `TranslationKnowledge/index.tsx`                   |
| 暂未参与执行的类型不再占据主要新增入口          | `EntryEditor.tsx`、相关文案                             |
| 把资料选择合并进统一翻译流程，减少嵌套弹窗        | `StudioTranslation.tsx`、`StudioKnowledgeTrial.tsx` |
| 修正规则“同维度即冲突”的策略              | `translation-knowledge/execution.ts`               |

对于规则冲突，我建议：结构化的互斥选项可以确定性判断；自由文本的同维度规则不能直接视为矛盾。无法可靠判断时，提示用户核对，**不要仅因文本不同就把两条规则一起排除**。

### 第二阶段：让日常维护足够便宜

增加术语行内编辑、批量粘贴、批量操作；支持从工作台就地添加资料和记住译法；提供清楚的命中与排除原因。

“保存本次设置”也放在这一阶段：让用户先完成一次有价值的翻译配置，再自然沉淀成可复用方案。

单文件、批量和转录后自动翻译，应共享资料选择的主要交互与状态规则。不同入口可以有不同限制，但不应该让用户重新学习三套相近的配置方式。

### 第三阶段：再补完整的表达、参考译文和自动积累

这些功能值得做，但应该在基础流程已经顺畅之后加入。否则是在一个已经难理解的系统上继续增加概念。

**现有的来源记录、版本摘要、本地采纳、任务快照、导入冲突和历史维护能力，应该保留。**例如执行器对条目状态、修订和摘要的一致性验证，是应该留在底层的正确能力。

迁移时尤其不能为了简化而批量清空旧条目的适用条件，也不能把导入候选自动改成可用。新交互可以简化默认路径，旧资料的真实约束仍需保留并清楚展示。

## 七、怎样判断这一轮改造真的有效

我会用下面这些任务作为验收标准，而不是只看页面是否更漂亮：

| 用户任务        | 应达到的体验                          |
| ----------- | ------------------------------- |
| 第一次添加一个固定译法 | 不创建对象、风格、方案，也能完成并用于翻译。          |
| 修改已经可用的术语   | 默认操作不会使它悄悄变回待审核。                |
| 一次整理多条术语    | 可以粘贴、检查和批量保存，不必逐条打开完整表单。        |
| 在工作台发现缺少一个词 | 不离开当前任务，就能添加并重新检查。              |
| 选择资料后发现没起效  | 能直接看见是未命中、未确认、范围不符，还是冲突，并有对应操作。 |
| 翻译下一份相似文件   | 能复用资料选择，但不会错误继承上一份字幕的说话者确认。     |
| 导入 AI 整理的资料 | 未确认的内容不会自动进入翻译请求。               |

**最终建议可以概括成一句话：保留严谨的知识系统，但不要让用户按知识系统的内部结构来工作。**

先把 **“写下一条译法 → 在当前字幕里选用 → 看见它被纳入 → 改错后顺手记住”** 做顺，再扩展复杂的对象关系、风格组合和自动学习。

目前最欠缺的不是更多教程，也不是更强的知识模型，而是：**一个不用先理解整个系统，就能立即获得价值的主流程。**
